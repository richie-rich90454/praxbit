# Secrets and configuration

Secrets belong in the process environment, never in the repository, the web bundle, or a log line.

## Production environment file

The server reads `.env` from the project root. It should be:

- Owned by the account that runs the process.
- Mode `0600` where the platform supports it.
- Outside version control; `.gitignore` excludes it.
- Backed up only in an encrypted location, or not backed up at all if it can be reissued.

```bash
cp .env.production.example .env
chmod 600 .env
```

On Windows, use the file properties or `icacls` to restrict access. Running as root is allowed; if you do, keep the checkout and `.env` readable only by root. A process manager may use `PRAXBIT_ENV_FILE` to point at another file outside the repository.

Do not commit a real `.env` file. The committed templates are `.env.example` and `.env.production.example`; both contain placeholders only.

## What is secret

| Value | Secret? | Notes |
| --- | --- | --- |
| `DATABASE_URL` | Yes | Contains the database password |
| `AI_API_KEY` | Yes | Provider billing credential |
| Session tokens | Yes | Stored hashed at rest; never log the raw value |
| CSRF tokens | Sensitive | Readable cookie by design; do not log |
| Backup off-box credentials | Yes | Use a restricted key, not a shared root key |
| TLS private keys | Yes | Managed by the proxy, never in this repository |
| `ADMIN_HANDLES` | No | Public if the handles are public; still avoid unnecessary disclosure |
| `PUBLIC_ORIGIN`, `CORS_ORIGINS` | No | Configuration |
| `PRAXBIT_LOAD_TOKEN` | Yes | Test credential; never commit |

## Handling rules

- Never put a secret in a `VITE_*` variable. Vite inlines those into the browser bundle.
- Never put an AI key in the client. The only path is the server gateway.
- Do not pass secrets as command-line arguments where other local users can read the process list. Prefer environment files or a `.pgpass`/service file.
- Do not echo a secret in a shell command, CI log, or error message.
- Do not log request bodies, `authorization`, `cookie`, or `x-csrf-token`.
- Do not include secrets in crash reports, screenshots, or Playwright traces. Review artifacts before upload.
- Use different credentials for development, test, staging, and production. Never reuse the production database password in CI.

## Generating credentials

Database password:

```bash
openssl rand -base64 32
```

Store it in the password manager or secret store, then set it in `DATABASE_URL` and the PostgreSQL role. Do not paste it into a ticket.

Session tokens are generated by the server with `crypto.randomBytes(32)`; there is no session signing secret to configure. The database stores only a SHA-256 hash.

## Rotation

Rotate a credential when it may have been exposed, when a person with access leaves, and on a scheduled interval appropriate to the risk.

1. Create the new credential without deleting the old one yet.
2. Update the environment file atomically.
3. Restart the service during a maintenance window.
4. Verify `/readyz`, login, sync, and the affected integration.
5. Revoke the old credential.
6. Record the rotation date and reason without recording the value.

For the database, create a new password for the role, update `DATABASE_URL`, restart, then confirm old connections are gone. For AI, create a new provider key, update `AI_API_KEY`, restart, then revoke the old key.

For a suspected session compromise, use `DELETE /api/v1/auth/sessions` or an admin database update to revoke sessions. The user must sign in again.

## CI

GitHub Actions must not contain production secrets. The CI workflow uses only a disposable PostgreSQL password (`praxbit_ci`) and no provider keys. If you add a deployment workflow, use an environment with protected secrets and require approval; do not put the key in a workflow file.

## Backup credentials

- The backup user needs read access to the database and write access to the backup directory.
- The off-box copy should use a restricted SSH key with a forced command or a bucket-scoped token.
- The backup destination should be encrypted at rest. The dump itself is not encrypted by `backup-postgres.sh`.
- Store the encryption key separately from the backup. A key next to the dump is not protection.

## Leak response

If a secret is exposed:

1. Revoke or rotate it immediately. Do not wait to understand the full scope.
2. Check logs for use of the old credential, within the retention window.
3. Revoke sessions if a session token or database credential was exposed.
4. Preserve relevant logs before rotating them out.
5. Follow [incident-response.md](incident-response.md).
6. Do not publish the secret in the incident ticket or chat. Use a private channel.

## Verification

- `grep -R` the repository for known key prefixes before a release. Do not commit the search results if they contain a value.
- Inspect the web build output for `AI_API_KEY`, `DATABASE_URL`, and provider tokens.
- Check that `infra/env/*.example` contains placeholders only.
- Check file modes on the production environment file and backup directory.
- Confirm the proxy does not log authorization headers or cookies.
